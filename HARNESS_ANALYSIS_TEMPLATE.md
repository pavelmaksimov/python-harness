# Шаблон анализа внедрения harness в `python-harness`

Используй этот шаблон перед добавлением нового catalog ID, нового артефакта к
существующему ID или существенным изменением install semantics. Оставляй
только применимые разделы. README остаётся источником истины каталога — этот
документ описывает решение и план, но не заменяет каталог.

Статусы анализа: `draft` → `ready for decision` → `approved` → `implemented`.
До статуса `approved` ничего не копировать в installable-набор и не менять
целевые проекты.

## 4. Классификация артефакта

### Предлагаемая классификация

| Поле | Решение |
|---|---|
| ID | `[kebab-case]` |
| Band | `[core | adapters | enforcement | agents | существующий ID]` |
| Kind | `[installable | reference | hybrid]` |
| Тип | `[rule | skill | hook | agent | companion/template | комбинация]` |
| Владелец продукта | `[этот repo | upstream]` |
| Триггер | `[globs / skill description / event / explicit delegation]` |
| Source path | `[harnesses/<type>/<id>/... | отсутствует для reference]` |
| Default target | `[.cursor/<type>/<id>/... | manual upstream step]` |
| Установка | `[always in bundle | derived | offer | manual/reference only]` |

### Почему выбран этот тип

- **Rule** — повторяемое руководство должно автоматически попадать в контекст
  при работе с подходящими файлами.
- **Skill** — руководство нужно по отдельной задаче и выгодно загружать
  on-demand.
- **Hook** — требуется детерминированное действие на событие, а не рассуждение
  модели.
- **Agent** — нужен автономный многошаговый workflow с собственным отчётом.
- **Reference** — продукт и установка принадлежат upstream; в каталоге нужны
  только ссылка, условия применения и интеграционные заметки.
- **Hybrid** — инструмент принадлежит upstream, а этот repo владеет локальным
  skill/rule/config companion.

Оставить только выбранное объяснение и уточнить его для конкретного случая.

**Готово, когда:** Kind отвечает на вопрос о владельце продукта, тип — на
вопрос о способе применения, а install path соответствует typed layout.

повторная установка имеет определённый и безопасный результат.

## 11. План проверки

Минимальный обязательный набор:

1. Отдельно просмотреть staged и unstaged diff.
2. Выполнить `git diff --check` для обоих состояний.
3. Проверить существование всех source paths из README.
4. Найти stale ID, sibling counts, bundle lists и application options в
   README, `AGENTS.md` и setup skill.
5. Провалидировать frontmatter, Markdown, YAML/TOML и runtime-specific
   descriptor фактическим поддерживаемым инструментом.
6. Проверить install/merge на минимальном fixture.
7. Повторить install/merge и доказать идемпотентность.
8. Запустить относящиеся к артефакту линтеры или тесты:
   `[точные команды]`.
9. Убедиться, что `VERSION` совпадает со строкой README до решения
   разработчика о релизе.

Дополнительные проверки по типу:

- **Rule:** триггер срабатывает на нужных globs и имеет pointer для guidance
  вне globs.
- **Skill:** description вызывает skill только в заявленных сценариях;
  длинные branches вынесены в siblings.
- **Hook:** событие, вход, выход, повторный запуск и ошибка детерминированы.
- **Agent:** descriptor поддерживается runtime; workflow заканчивается
  проверяемым отчётом.
- **Config companion:** merge валиден, не создаёт overlap и повторяется без
  изменений.

**Готово, когда:** у каждого критерия приёмки есть команда, fixture или
инспекция, способная доказать его выполнение.
